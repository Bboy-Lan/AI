# 管理员自己发的评价也不用再审，也不再提醒自己（2026-11-10）

用户反馈："管理员的一系列操作还不需要审核的，包括管理员的评论、帖子等，也无需在消息提示里提醒管理员。"

## 一、查到的真实缺口

上一轮已经把管理员发布的**推荐、消费经历、树洞话题、楼层回复**改成服务端按运行时身份直接 `approved`，但**评价（评论）漏了一处**：

```js
// server/classic/xsyj_web_v1/native/food/index.js · upsertReview
...reviewPolicy.resubmit(current),        // ← 没传第二个参数，管理员也走 pending
...reviewPolicy.resubmit(current, verifiedAdmin)  // ← 现在
```

`resubmit(row, admin)` 的第二个参数默认 `false`，漏传就等于"管理员写了评价也要排队等审"：评价落成 `reviewTag:'pending'`，进集中审核台、点亮待办角标，管理员还得自己给自己点一次"通过"。演示仓储（`src/demo/repository.ts`）那边一直是 `actor().isAdmin?'approved':'pending'`，所以本地完全看不出问题——这也是它一直没被发现的原因。

顺带两处"自己提醒自己"的口子：

- `moderation.cjs` 的 `notify()` 会通知内容的 `ownerOpenId`。管理员处理到自己名下的内容时，会收到一条"你的评价被标记为…"的通知，等于自己给自己发提醒。
- `image-review.cjs` 驳回图片时给作者发通知，同样没排除"管理员驳回自己的图"。

## 二、改动

| 位置 | 改动 |
| --- | --- |
| `native/food/index.js` `upsertReview` | 事务前先算 `verifiedAdmin = Boolean(await adminFor(id))`，`resubmit(current, verifiedAdmin)`；管理员评价直接 `approved`，普通用户仍 `pending`。 |
| `moderation.cjs` `notify` | `if(!r.ownerOpenId \|\| r.ownerOpenId === uid) return` —— 操作人就是作者时不再写 `xsyj_review_notifications`。 |
| `image-review.cjs` | 驳回通知只发给"不是操作人本人"的作者。 |

没有新增集合、没有改表结构；`xsyj_review_notifications` 仍是私有集合，审核审计照旧写 `xsyj_review_audit`。

**历史数据**：新脚本 `scripts/approve-admin-pending.mjs`（默认 dry-run，`--apply` 才写库）按 `xsyj_admins` 里的启用账号，扫描五类内容的 `reviewTag='pending'`（含无标签但 `status='pending'` 的老记录）。本机跑 dry-run 的结果是五类全部 **0 条**（管理员账号 1 个），也就是线上没有遗留的"管理员待审内容"需要迁移——所以这次一条真实业务记录都没改，证据见 `docs/evidence/ux-admin-self-approve-20261110.json`。

## 三、验证

- **自动测试 125 项**全通过（新增 `tests/admin-self-review.test.ts` 4 项）：
  1. `resubmit` 策略：管理员四种状态都判 `approved`、普通用户始终 `pending`、管理员改自己被打回的内容仍保持隐藏；
  2. **源码守卫**：扫 `review-policy.resubmit(` 的所有调用点，要求每处都显式传第二个参数（这次漏传就是这样漏掉的），并单独钉住评价这一处；
  3. 管理员审自己的内容 → `xsyj_review_notifications` 一条都不写；
  4. 审别人的内容 → 照常给作者写一条（`ownerOpenId=owner, actor=admin`）。
  `deploy.mjs` 门禁已加入 `tests/admin-self-review.test.ts`。
- **真实云端 82/82**（3 个一次性账号、7 张临时图片、3 条直插记录跑完自动清理，`failure=""`、`cleanupFailure=""`）。本轮新增三条断言全部通过：`管理员写评价默认已审核`、`管理员评价在其他账号看来也是已审核`、`管理员操作不给自己产生审核提醒`。同轮既有断言（管理员经历/话题免审、普通用户待审只对自己可见、待办角标 ≥ 审核台待审数、普通账号待办为 0）没有回退。
- 前端没有改代码：管理员评价变 `approved` 后，徽章与审核台自然不再显示，待办角标也不再因为自己的操作亮起。构建产物仍是 `index-B_HOo9zM.js` + `index-DpZuNb_y.css`，两站读回维持 19/19（同一份资源）。

## 四、一个相关但没动的边界

待审**评价**在服务端 `listReviews` 里没有按 `reviewTag` 过滤，网页详情页也只用 `status!=='hidden'` 过滤（推荐/经历/话题/楼层都已经按"非 approved 只有作者与管理员可见"处理）。也就是说普通用户刚写的待审评价，别人目前仍能看到正文并计入均分——这属于"评价的可见性"问题，与本轮"管理员免审"不是同一件事，改动会让评价在通过审核前从公开页消失、均分也会变化，所以先按原样保留并在此记录，等确认后再单独做。

其余边界同前：只在昆明服务范围内、未在实体机/微信内置浏览器逐机型验证审核提醒的到达时机；管理员发布的免审依赖 `xsyj_admins` 里 `enabled:true` 的运行时判定，前端声明的身份一律不采信。
